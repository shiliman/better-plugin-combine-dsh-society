# 设计说明

这份文档解释"办公厅"为什么长这样，以及哪些地方是刻意不做的。

## 问题

插件越多，模型越记不住。两条路都不成立：

- **把所有插件卡都塞进系统提示**：每张卡几百字，每轮都在烧 token，而且九成和当前任务无关；
- **一个都不给**：模型只能靠猜，猜错就说"我没有这个能力"。

真正需要的不是"知道所有细节"，而是**知道去哪查**。

---

## 三层结构（越往下越贵）

```
L0  目录卡     每个部门一张卡：职能 / 工具 / 入口 / 数据 / 状态
L1  索引      平时只留一行；关键词命中才展开成卡
L2  转交      能答就答；要动手就交给原部门
```

一次性全给（L0 常驻）太贵；什么都不给（L2 直接）太蠢。所以默认走 L1：系统提示里只有一行"有这事先查目录"，具体内容等问了再展开。

一次 `office_catalog` 调用 ≈ 1 秒 + 几百 token；全部卡片常驻 ≈ 每轮几万 token。差三个数量级。

---

## 五条硬约束

### 1. 不建第二份真相

不复制、不聚合、不落库。目录缓存只是一份"上一轮扫描的 JSON"，带生成时间；它显示的数据目录 mtime、记忆条数都是当场读出来的。插件升级、数据变动，下次扫描自然就变，不存在"缓存和实际打架"。

判据：如果这份缓存被删掉，功能是否完全不受影响？——是。

### 2. 只读

- 不写记忆库（SQLite 以 `readOnly: true` 打开）；
- 不改插件配置；
- 不执行任何部门的能力；
- 不碰密钥（密钥类插件的卡片只显示"有设置页"，不显示值）。

需要动手时输出一句"归 X 部门，入口在 Y，要我把会话开起来吗"，把决定权交回。

### 3. 懒更新

没有后台轮询、没有守护进程、没有定时任务。每次查询时比较缓存 mtime：

- `office_catalog` 每次都重扫（约 1 秒，保证新鲜）；
- `office_ask` 复用 10 分钟内的目录缓存。

没人在用的时候，它不消耗任何资源。

### 4. 不建自己的记忆库

目录是结构化数据（JSON），不是"记忆"。它不往 meow-memory 里写任何东西——否则又多一个会过期、要维护的真相源。

想记住"某部门在干什么"，那是各部门自己的事。

### 5. 归组两条腿

插件 → 工具的映射靠两条独立证据：

- **静态扫**：包内宿主侧 JS 里的 `tools.register({ name: 'xxx' })` / `name: 'xxx' … parameters:`；
- **运行时对账**：宿主侧插件本身知道当前 Agent 能调用哪些工具（`Tool.listTools`）。

两者对不上就标「未静态识别」——**宁可空着，也不猜**。测试时实测 30+ 个包里约 1/3 扫不到工具名（动态拼接、压缩产物、纯 UI 插件），这些卡片的 `tools` 是空数组，`duty` 照常显示。

## 扫描器实现要点

### 工具名为什么用正则而不是 AST

插件包形态太杂：ESM / CJS / 打包后的单文件 / 转译产物 / 压缩混淆。接一个解析器要处理所有方言，而正则只需要覆盖三种写法：

```js
name: 'lower_snake' …… parameters:      // 字面量
name: TOOL_CONST …… parameters:         // 常量表
tools.register({ name: 'lower_snake' }) // 直接注册
```

三个坑，都踩过：

1. **注释被当成代码**：文档里的示例 `name: 'xxx' … parameters:` 会让卡片多出假工具。做法：整行去掉以 `//`、`/*`、`*` 开头的行再匹配。
2. **`\u4FEE` 形式的转义**：打包产物里中文常写成 `\uXXXX`，直接显示就是乱码。加一层 `decodeEscapes` 还原。
3. **入口抓成整句**：`client.js` 里第一个 `title:` 往往是一句说明。只接受 ≤10 字、不含标点、不是句子的标签，否则只写"设置页"。

### 数据目录怎么找

不扫全盘，只按名字猜三档：

```
$DSH_HOME/storages/<包全名 | 去 scope | 去 dsh- 前缀>
$DSH_HOME/<同样三个>
$DSH_HOME/<把 -scroll 换成 -duty>        # 刷类插件的历史命名
```

外加黑名单（`sessions`、`profiles`、`skills`、`dsh-runtimes` 等），避免把系统目录误认成插件数据目录。

### 记忆为什么不用向量库

量级不对：几十个部门、几个库、几千条记忆。BM25 级别的关键词检索足够，而且**结果是可解释的**——用户能看懂"因为这条标题里有『贴吧』所以排第一"。

向量检索在这个规模上带来的是：多一个 embedding 依赖、一次性的建库成本、以及无法解释的排序。不值得。

## 检索打分

```
score = Σ over terms ( min(count(content, term), 4)      // 正文出现次数，封顶 4
                      + 4 × hit(title)
                      + 3 × hit(keywords) ) × term.weight
score *= 1 + 0.35 × min(matched_terms, 4)                // 命中词数比单词重复更重要
```

**3-gram 补召回**：中文长句没有空格可切，整句当一个词查会漏。做法是给含中文、长度 ≥6 的词补一组 3-gram（步长 2，权重 0.25）。

这里踩过一个坑：早期对所有 >12 字符的词无条件补 gram，结果查 `dsh-daily-notes` 时"dsh"把 588 条不相干记忆全捞了上来。修正为**只对中文补**，并对正文计数与命中词数都封顶。

---

## 刻意不做的

| 不做 | 为什么 |
|---|---|
| 后台轮询 / 定时扫描 | 没人查的时候不该耗资源；查询时重扫只要 1 秒 |
| 常驻全部部门卡 | 每轮几万 token 换一个"可能用得上" |
| 代执行 | 一旦能动手，"只读"就没了；转交比代跑更安全 |
| 自己的记忆库 | 多一个真相源 = 多一处过期 |
| 向量检索 | 规模不够，可解释性更重要 |

## 另一种宿主

`catalog.json` 是纯数据，不绑 DSH。`examples/tiny_host.py` 演示了怎么在任何 Python 程序里读同一份目录 + 查同一批记忆库——桌宠、面板、CLI 都能用。
